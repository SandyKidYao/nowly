# 此刻 · Nowly：Android MVP 技术选型建议

**建议采用 Kotlin 原生 Android：Jetpack Compose + Room + AlarmManager。** 首版做一个完全在本机运行的应用；页面和业务逻辑用 Kotlin，实现提醒时直接使用 Android 系统能力。当前最值得投入的工程成本是通知可靠性、状态一致性和数据不丢失。

用户已于 2026-09-18 确认本技术选型并授权初始化工程；本文中明确标为待定的行为规则仍需后续规格细化。判断依据是 `docs/` 下的需求 v8 与定稿线框 v0.8；二者描述的是首版，未来 iOS、云同步和健康设备等仅作扩展分析，不视为已承诺路线图。暂按没有必须沿用的团队技术栈、首批本人使用、iOS 尚未排期判断；团队经验或平台计划改变时，应按下文重新评估。实际工程基线及实现范围以 README 为准。

## 1. 为什么这个产品适合原生 Android

| 产品要求 | 对技术选型的影响 |
| --- | --- |
| Android 首发，首先本人使用 | 优先降低单平台交付与调试成本；跨平台代码复用暂时没有直接收益 |
| 每日自定义提醒时间；划掉、跳过、替换各有含义 | 核心逻辑依赖系统通知、广播、后台调度和权限，直接使用 Android API 更便于诊断 |
| 无登录、无云同步，所有记录在手机本地 | 使用本地关系数据库，不需要后端、云数据库、推送服务或网络权限 |
| 选项 ID 稳定，改名同步历史与统计 | 需要外键关联和按 ID 聚合，适合 Room/SQLite；不适合把整份记录塞入偏好设置或 JSON 文件 |
| 选择即保存，立即返回来源 | 数据提交与退出必须有先后关系；通知入口还需要专门处理任务栈 |
| 三类统计、时间轴、无限滚动历史 | Compose 足以承载；无需 WebView、通用问卷引擎或复杂 BI 系统 |

官方推荐 Compose、ViewModel、协程/Flow 和 repository 分层。这里的判断是：Nowly 可以采用这些常规 Android 组件，以较少的技术层次完成已经确认的流程。[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)

## 2. 候选方案：什么条件下改选

下表是针对 Nowly 的工程判断，不是框架性能实测或普适排名。各框架都能做出这些页面，差异主要在平台边界、团队熟练度和未来复用收益。

| 方案 | 对当前 MVP 的价值 | 需要承担的成本 | 建议 |
| --- | --- | --- | --- |
| Kotlin + Jetpack Compose | 直接处理系统提醒、通知事件、生命周期和本地数据；单一语言调试 | 以后做 iOS 需要新增平台实现，Android 专属代码不能直接搬过去 | **首选**：Android 优先、团队无固定栈时 |
| Flutter + Dart | Android/iOS 共用大量界面与业务代码，适合明确的双端计划 | 要核验通知插件是否覆盖清除回调、替换、精确闹钟与重启；缺口需要 Kotlin 原生适配，调试涉及两侧 | **备选**：团队熟悉 Flutter，或 iOS 已排入紧接着的版本 |
| React Native + TypeScript | 可以利用已有 React/TS 人员与组件经验 | 核心通知语义仍要原生模块或满足要求的库；不能仅凭 JS 定时器完成后台提醒 | 已有强 React 团队时进入短验证，当前没有必须选择它的依据 |
| Kotlin Multiplatform / Compose Multiplatform | 可以共享业务代码，进一步共享界面；保留 Kotlin 投资 | 现在就引入跨平台构建、依赖兼容和平台实现的管理成本 | 暂不启用；iOS 立项时再评估逐步抽取 |
| WebView / PWA | Web 页面开发可复用 | 仍需补原生提醒和数据层，与本项目的核心难点重合 | 不作为本次主方案 |

Flutter 官方提供平台通道，React Native 提供原生平台扩展；它们不是无法实现提醒，而是不能消除底层平台适配工作。[Flutter 平台通道](https://docs.flutter.dev/platform-integration/platform-channels)、[React Native 原生平台](https://reactnative.dev/docs/native-platform)

Kotlin Multiplatform 支持逐步共享业务逻辑；先用 Kotlin 不等于以后必须推倒重来，也不等于已经免费获得 iOS 版本。迁移时仍需调整平台依赖、时间 API、存储与通知适配。[KMP 共享代码](https://kotlinlang.org/docs/multiplatform-share-on-platforms.html)、[从既有 Android 应用接入 iOS](https://kotlinlang.org/docs/multiplatform-mobile-integrate-in-existing-app.html)

## 3. 推荐技术栈

| 层次 | 首版选择 | 在 Nowly 中负责什么 |
| --- | --- | --- |
| 语言与开发工具 | Kotlin、Android Studio、Gradle Kotlin DSL | 一个 Android 工程；固定 Gradle Wrapper、AGP、Kotlin 和配套 JDK 版本 |
| 界面 | Jetpack Compose + Material 3 | 首页、项目表单、回答、历史和统计；按线框定制样式，不强制采用默认视觉 |
| 页面状态 | AndroidX ViewModel + Coroutines + StateFlow | 从数据库读取状态；接收操作；保存完成后才通知界面返回 |
| 导航 | Navigation 3 稳定版 | 主应用页面栈；没有底部导航。通知回答使用独立轻量 Activity 承载相同回答组件 |
| 业务结构 | 按功能分包；repository + 少量业务操作类 | 集中处理回答、跳过、替换、调度和统计，避免 UI 与 Receiver 各写一套规则 |
| 依赖组装 | 构造函数注入 + 一个 AppContainer | 首版手动组装数据库、仓库和系统适配器；规模变大后再评估 Hilt |
| 核心存储 | Room + SQLite；编译处理使用配套 KSP | 项目、选项、时间点、提醒实例、状态与答案；事务、索引、迁移 |
| 少量偏好 | Preferences DataStore，确有需要时加入 | 权限提示是否展示等非核心偏好；项目提醒开关和初始化标记仍随业务库管理 |
| 提醒调度 | AlarmManager + 显式 PendingIntent + BroadcastReceiver | 定时触发、重建计划；不靠应用进程持续存活 |
| 通知 | NotificationCompat + NotificationManagerCompat | 每项目最新通知、点击回答、跳过动作、清除回调、通知渠道 |
| 时间处理 | java.time + 可替换 Clock | 分离每日本地时刻、绝对时间戳和时区；测试时可控制时间 |
| 历史加载 | Room 游标分页 + LazyColumn | 按稳定排序键追加历史，不把所有记录一次性加载；复杂度增加后可接 Paging 3 |
| 图表与时间轴 | Compose 布局/Canvas | 先做简单堆叠分布和条形统计；附文字数量、图例与无障碍语义 |
| 测试 | JUnit、协程测试、Room 仪器测试、Compose UI 测试 | 重点覆盖状态竞争、时间规则、迁移和最短记录流程 |
| 分发 | 持续使用同一签名的 release APK | 首批直接安装；固定 applicationId、递增 versionCode、保存签名密钥，支持覆盖升级 |

Room 为 SQLite 提供查询检查、数据访问与迁移支持，适合本项目的关系型数据。[Room 官方说明](https://developer.android.com/training/data-storage/room)

截至本次查询，Navigation 3 已有稳定版本；初始化工程时选稳定通道，不照抄文档中的预发布示例。依赖版本在建立工程时形成一组可构建的锁定组合，本报告不把未经构建验证的整套版本号写成既成事实。[Navigation 3 发布页](https://developer.android.com/jetpack/androidx/releases/navigation3)

最低版本暂建议 **Android 8.0 / API 26**，以统一通知渠道和平台时间 API；这是本项目的兼容成本取舍，不是 Compose 的最低要求。拿到首批手机型号后再确认。compileSdk/targetSdk 采用建项时已稳定、工具链支持的 SDK，并按目标版本行为做回归；对外上架时再核对商店当时要求。

首版不引入后端、账号 SDK、FCM、常驻前台服务、WorkManager 定时提醒或重型图表库。后续云同步出现时，WorkManager 可以承担可延迟的同步任务；它不承担当前的时刻提醒。

## 4. 最关键的选型：提醒与通知

### 4.1 采用 AlarmManager，精度策略单独明确

建议将“尽量接近用户指定的时刻提醒”作为需要确认的产品目标。若要求在休眠时仍接近设定时刻，采用获得授权后的 `setExactAndAllowWhileIdle()`；按每日时间表展开一次性闹钟并补齐后续安排，不依赖重复闹钟的精确性。时间点配置保存在 Room，重启、修改时区/系统时间、编辑计划及应用恢复时统一重建。[Android 闹钟调度](https://developer.android.com/develop/background-work/services/alarms)

权限分两层：Android 13+ 的 `POST_NOTIFICATIONS` 决定能否发普通通知；精确闹钟另需检查 `canScheduleExactAlarms()`，使用 `SCHEDULE_EXACT_ALARM` 时需要系统特殊访问授权。后者是系统设置入口，不能承诺只用一次通知弹窗完成。首版不直接采用用例受限的 `USE_EXACT_ALARM`。[通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)、[精确闹钟权限](https://developer.android.com/develop/background-work/services/alarms#declare-the-appropriate-exact-alarm-permission)

**建议的未授权策略，待规格确认：** 通知权限未获准时，保留项目开关的用户意图，不伪造“已成功通知”；精确权限未获准时，可以降为允许延迟的提醒，但必须让用户知道可能延迟。恢复授权入口放在既有页面的轻量提示/操作中，具体位置需补充评审，不新增全局设置页或独立权限引导页。

### 4.2 原生也不能绕过系统限制

休眠时允许唤醒的闹钟仍受频率限制。官方 Doze 文档说明限制按整个 App 计算，而非按项目；因此不同项目相隔几分钟的提醒，也不能一概承诺逐分钟准时。[Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

建议同一时刻只做一次系统唤醒，再给各项目分别发通知；接近但不同的时刻是否允许延迟，留待规格与真机结果决定，不擅自合并用户的配置。关机、强制停止、用户关闭渠道、厂商后台限制也不能由框架提供绝对送达保证。Android 15 明确会在应用进入停止状态时取消 PendingIntent，恢复后需要重建。[Android 15 停止状态](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state)

首版应记录计划时刻、回调到达时刻和通知提交结果用于开发诊断；这些信息不能证明用户已经看见通知。未送达或渠道禁用也不能算用户“跳过”。这属于内部诊断，不新增用户状态页面。

### 4.3 每项目替换通知，每实例标识回调

同一项目使用稳定的通知 tag/id，因此新通知可以替换旧通知；每次提醒另外生成唯一的 `occurrenceId`。点击、跳过、清除分别使用带实例身份的 PendingIntent，不能只把最新实例 ID 写入同一个可被覆盖的 extras。

点击通知用 `PendingIntent.getActivity()` 直接进入回答界面。跳过动作与 `deleteIntent` 进入显式 Receiver，由同一业务入口提交状态。系统接口为单条划掉和“全部清除”提供 `deleteIntent`；程序主动取消、点击打开、系统回收不能笼统当成用户跳过。[Notification.deleteIntent](https://developer.android.com/reference/android/app/Notification#deleteIntent)

### 4.4 四种状态必须落到数据库

| 当前状态 | 事件 | 结果 | 是否保存答案 |
| --- | --- | --- | --- |
| 待处理 | 用户选择选项并提交成功 | 已回答 | 是；保存 optionId 与实际选择时刻 |
| 待处理 | 跳过按钮、划掉、全部清除的回调 | 已跳过 | 否 |
| 待处理 | 同项目新提醒成为当前提醒 | 未处理 | 否 |
| 待处理 | 仅仅过去一段时间 | 仍待处理 | 否 |
| 已结束 | 重复点击、重复广播、旧实例回调 | 保持原结果 | 不重复写入 |

建议每个项目的通知更新/取消进入同一串行处理入口，数据库事务检查实例是否仍待处理及是否为当前实例。回答、跳过、替换竞争时，只允许一次有效终结；旧实例的迟到清除回调不能修改新实例。最终竞争优先级需在规格中确认。

Room 事务不能覆盖 Android 的通知调用。应持久化期望的通知动作或可重建信息，使发布与取消可重复执行、可恢复，并在下次有效入口对账；不能把“写数据库后调用 notify”当成两个系统之间的原子操作。PoC 要主动在两者之间杀进程，验证恢复路径与无法即时恢复的边界。

### 4.5 保存后返回来源，需要单独设计导航

建议主界面由 MainActivity 承载，通知专用回答由轻量 AnswerActivity 承载，二者复用同一个 Compose 回答组件和保存逻辑。通知 Activity 使用独立任务配置，提交成功后关闭；App 内回答则弹出当前页面。避免通知回答完成后总是跳到首页或破坏主应用原有页面栈。[从通知启动 Activity](https://developer.android.com/develop/ui/views/notifications/navigation)

时序必须是：用户点选时捕获时间 → 校验当前实例 → 数据库提交 → 安全清除对应通知 → 返回。不可先退出再异步保存；失败时不能显示为成功或吞掉错误。异常恢复采用原页保留与诊断，具体提示待规格确定，不增加独立失败页。

## 5. 数据模型：现在保持简单，将来留得住数据

以下是概念模型，字段名仅供规格和建表时参考，不是最终数据库定义。

| 对象 | 主要信息 | 关键规则 |
| --- | --- | --- |
| Project | UUID、名称、一个问题、remindersEnabled、scheduleRevision | 开关是用户意图，不等于系统已授权；版本用于识别失效计划 |
| AnswerOption | UUID、projectId、当前名称、显示顺序、isActive | 改名保留 ID；被引用的选项移出可选列表后仍可解析 |
| ReminderTime | UUID、projectId、每日 LocalTime | 时间点稳定身份，不以列表下标标识；不存成固定 24 小时间隔 |
| SampleOccurrence | UUID、projectId、计划时刻、回调时刻、status、optionId?、answeredAt?、回答时区/偏移 | 每次采样一个实例；只有已回答可拥有答案和填写时间 |
| AppMetadata | 数据库初始化版本/标记 | 首次预置心情与标记在同一事务完成；删空项目后不会自动重新生成 |

回答与状态放在同一采样实例中，首版无需额外建立通用多问题问卷表。项目、选项、记录都采用 UUID，便于后续导出或引入云同步时稳定识别。通过约束/事务保证 optionId 属于该项目，保留历史引用，按业务查询建立 projectId、时间和状态索引。

**标签规则：** 展示时通过 optionId 关联当前名称；统计按 ID 分组。同名选项不自动合并；停用选项的历史仍计入统计。颜色也应按稳定 ID 保持对应，不能因排序改变就让同一标签换色。项目删除是否连带删除历史仍待确认，此处不预设不可逆级联删除。

**时间规则：** 保存绝对时间戳，并保留回答当时的时区/偏移；每日提醒用当地时刻生成下一次触发。建议历史按填写时当地日期与小时归组，避免旅行后旧数据随当前时区漂移；这属于待确认口径。夏令时缺失/重复时刻、改时区后的当天安排要独立定义，不能简单“昨日时间戳 + 24 小时”。

**分页规则：** 采用带 ID 的稳定游标，避免同一时刻多条记录漏读或重复。已回答按填写时刻还是全部按提醒时刻排列，需统一确定；可以在查询中形成同一展示排序键，不能照搬原型里按计划时间排序的演示逻辑。

## 6. 统计与本地可靠性

三张图共用同一个日期范围和同一批已回答数据：日期趋势建议先用每日选项占比分布；时段图展示各时段选项分布；选项图展示次数/占比。空数据为无回答，不能画成“压力为零”。实际图形和时段边界仍待确认。

普通分类没有数值高低；有序等级也不能自动等同等距分数。首版统一展示分布，不根据选项序号计算平均压力或画连续数值趋势。未处理、跳过不进入答案占比分母；若展示它们的数量，要另定日期归属。线框里的“普通分类/有序等级”切换仍属于待规格细化的内容。

首版用 Compose 布局和 Canvas 就能实现这些简单图形。仅当明确需要缩放、多轴、复杂标注等能力时，再选图表库；无障碍信息必须提供可读的标签、次数和占比。

数据库放在 App 私有目录；首次创建、选项编辑和回答终结使用事务。持续导出 Room schema、测试升级迁移，不开启会清空旧库的 destructive migration。用同一签名覆盖安装验证升级后记录仍在。首版默认不加数据库加密 SDK；平台私有目录保护不等于抵御 root、解锁后的物理访问或提供独立数据库加密。

“仅保存在本机”还需要处理 Android 默认自动备份。建议显式关闭云备份，并配置相应版本的备份/迁移排除规则；不能只写一个 allowBackup=false 就假定所有厂商的设备迁移都被禁用。按首批设备验证。[Android Auto Backup](https://developer.android.com/identity/data/autobackup)

因此，首版没有导出/恢复时，卸载、清除数据或丢失手机可能导致记录无法恢复。这是当前范围的真实代价。建议后续优先级先考虑用户可控的导出/备份，再考虑账号和同步。不要通过接入云分析或崩溃 SDK 让问题文案、心理状态答案意外离开设备；开发诊断仅保留必要的内部标识、时刻和错误码。

## 7. 架构规模与未来演进

首版一个 app 模块即可，按 projects、recording、history、statistics、data、platform 分包。UI 读 ViewModel 状态，ViewModel 和 Receiver 调用共享业务入口，业务通过 repository 读写 Room；AlarmManager 与通知适配器只负责系统交互。没有必要从第一天建立十几个 Gradle 模块或给每次数据库读取都包一层用例。

| 后续方向，均未纳入本次 MVP | 现在保留的边界 | 真正立项时仍要增加的工作 |
| --- | --- | --- |
| 导出/恢复 | UUID、清晰实体、可追踪 schema 迁移 | 导出格式版本、文件选择、恢复校验、冲突与隐私处理 |
| iOS | 统计、校验、状态转换不依赖 Activity/Context；系统提醒封装接口 | 评估 KMP 或独立 iOS；重做通知适配、权限、后台及返回体验；共享比例需验证 |
| 账号/云同步 | repository 作为数据边界、客户端生成稳定 ID | 账号、服务端、上传队列、冲突规则、删除同步、安全与部署；不能只“加一个 API” |
| 多题、数值、自由文本 | 记录与选项身份清晰；不把压力示例硬编码成产品类型 | 扩展问题/答案模型并迁移数据，重定统计口径；首版不先造通用问卷引擎 |
| 健康数据/设备 | 设备访问留在平台适配层 | 独立权限和采集链路；设备时间、手动回答时间不能混用 |
| 多人研究 | 保持个人本地产品简单 | 这是新的权限、协作与数据治理问题，需要重新做产品和服务端设计 |

采用原生的长期成本是增加第二个平台时会有实质工作；现在获得的是 Android 首版更直接的调试路径。未来需求只决定今天保留哪些边界，不要求今天先实现那些能力。

## 8. 建议的验证顺序与决策点

| 顺序 | 验证内容 | 通过的可观察证据 |
| --- | --- | --- |
| 1. 先做最小提醒 PoC | 一个项目、两个时刻、一个回答按钮、本地保存；再增加第二项目 | 真机能收到提醒，点选后记录落库且返回来源；划掉/跳过/替换分别得到正确状态 |
| 2. 验证系统边界 | 熄屏休眠、普通杀进程、强制停止后重开、重启解锁、通知/精确权限撤回 | 明确哪些情况能恢复、哪些受系统限制；按计划时刻与回调时刻记录实际延迟 |
| 3. 验证一致性 | 回答/跳过/新提醒并发、重复事件、提交和通知之间杀进程 | 每实例最多一个终结结果；旧回调不影响新通知；不能出现已返回但无记录 |
| 4. 完成业务页面 | 创建编辑、时间轴、历史分页、三类统计 | 与定稿线框流程相符；改名后历史与图表名称改变，ID、时间和次数不变 |
| 5. 验证长期使用 | 数据库迁移、同签名覆盖升级、跨日/时区、连续日常使用 | 旧记录不丢失；新增/停用选项无孤立引用；所有统计能由同一记录集复算 |

先用发起人的实际手机验证，再补最低支持版本、Android 12 的精确闹钟权限边界、Android 13+ 通知权限及拟支持的新系统。若需要覆盖其他厂商，应增加对应真机。一次模拟器成功不能作为提醒可靠性的验收证据。PoC 可先安排 1–2 个专注开发日，连续日常观察另计；这是验证预算建议，不是整个 MVP 的工期承诺。

以下事项影响行为规格，不能由选型报告替用户默默确定：

1. 指定时刻允许多大延迟；精确权限被拒后是否接受延迟提醒。
2. 发起人的手机型号/系统，以及是否有已排期的 iOS 计划和已有团队技术偏好。
3. 旧回答页打开时新提醒到来，回答/跳过/替换的竞争如何处理。
4. 暂停项目、删除项目与既有待处理通知、历史的关系。
5. 历史与统计的时区、日期归属，以及等级/分类的最终展示规则。

**可据此推进的结论：先按 Kotlin + Compose + Room + AlarmManager 验证核心链路；提醒 PoC 通过后完成其余 MVP。** 如果近期双端已经明确，或团队熟悉的跨平台栈能显著缩短交付，则在建正式工程前，把同一提醒验收用例用于 Flutter/RN 短验证，再决定是否改选。
